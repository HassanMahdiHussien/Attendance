# Feature Specification: Attendance transaction import and punch cleanup

**Branch**: `502-attendance-import` | **Created**: 2026-10-22 | **Status**: Clarified 2026-10-22

**Input**: ROADMAP §5 spec 502 — import batches, raw transactions, device roles, duplicate protection, punch cleanup, restaurant counts, contractors and visitors. Requirements: PRD §4, §7, §8, §15, §23; ROADMAP §2 (devices; contractors/visitors not assessed) and §3 (sample findings). Depends on spec 501 (employee record). No attendance calculation (sessions, lateness, absence) is built here — that is spec 503; this spec delivers clean, trustworthy punches and their coverage.

## Sample file (design sample, real names — never committed)

`Transaction_20261020084331.xlsx`: title "Transaction" in row 1, header in row 2: `Employee ID`, `First Name`, `Department`, `Date` (`YYYY-MM-DD`), `Time` (`HH:MM`, no seconds), `Punch State` (`Check In` / `Check Out` / `255`), `Serial Number`, `Device Name`, `Data Sources`. 4,828 rows, 18–20 Oct 2026, 6 devices (Hilla and Karbala: In, Out, Restaurant). The file name carries the export time (`20261020084331` = 2026-10-20 08:43:31); the last punch is 08:41 on that day, so the last day is partial.
- 907 rows are exact duplicates (minute precision). 1,201 restaurant rows (`255`).
- 578 distinct IDs: 504 eight-digit, 74 shorter. 472 of the eight-digit IDs are employees in `HC.xlsx`; the rest are mostly `3rd Party …` contractors, plus one `SC Department` ID missing from HC. ID length does **not** identify contractors.
- Punch state always matches the device (`*_In_Face` → Check In, `*_Out_Face` → Check Out, `*_RESTAURANT_Face` / `*_RESTARRANT_Face` → 255).

## Clarifications (product owner, 2026-10-22)

- **Unknown IDs**: every punch is stored. An ID not in the employee list whose department label marks a non-employee (`3rd Party …`, `Guest`, `General` — a configurable list) is a **non-employee** (contractor/visitor): never assessed, but counted in attendance and restaurant reports. Any other unknown ID raises an HR **data issue** ("punches for an ID not in the employee list"), grouped per ID per batch.
- **Coverage**: the system suggests the coverage of each upload — from the first punch date to the export time read from the file name `Transaction_YYYYMMDDhhmmss` (or the last punch when the name has no timestamp) — for the sites whose devices appear in the file. HR confirms or edits it before commit. Time outside confirmed coverage is "not covered" and later specs treat it as pending, never absent.
- **Devices**: keyed by serial number. A new serial is registered with a suggested role (check-in / check-out / restaurant, from the punch state and device name) and site (branch, from the name prefix such as `Hilla_`), status **pending approval**. Its punches are stored but not used (not cleaned, not counted) until HR approves the device once; approving re-processes its stored punches. Approved devices are used straight away. HR can change a device's role or site later with an effective date; changes re-process affected punches.

## Requirements

- **FR-001 Upload and batch**: HR uploads `.xlsx` or `.csv`. Column mapping reuses the spec-501 positional mapping (saved per header signature; the title row above the header is detected and skipped). Each committed upload is an append-only `attendance_import_batches` row: original file on the private disk, SHA-256, uploader, time, confirmed coverage (date-time range + branches), counts and a summary (counts and codes only). The same file (by hash) cannot be committed twice.
- **FR-002 Preview before commit**: rows read; new transactions; duplicates of already stored transactions (from earlier or overlapping files); exact duplicate rows inside the file; transactions per device and per day; new devices (pending approval); unknown IDs split into non-employees and data issues; suggested coverage; errors (bad date/time, unknown punch state). Nothing is written before HR confirms.
- **FR-003 Raw transactions are immutable**: `attendance_transactions` keeps every source row exactly as read (ID text, name, department, date, time, punch state, serial, device name, source), its batch and row number, and a **natural key** (`company_id`, `person_code`, `punched_at`, `punch_state`, `serial_number`). Re-uploading the same or an overlapping file never creates a second transaction with the same natural key; it records that the batch also contained it (`attendance_transaction_sources`: transaction ↔ batch ↔ row) so every source row stays traceable. Append-only triggers.
- **FR-004 Times**: `punched_at` = `Date` + `Time` in Asia/Baghdad, stored as local date-time (minute precision kept as given). The original strings are kept too.
- **FR-005 People**: each transaction is linked to an employee (by `employees.employee_code`, exact text) or classified as non-employee or unknown per the clarification. The link is re-evaluated when the employee list changes (spec 501 import), never by editing the raw row.
- **FR-006 Punch cleanup** (PRD §8), per person, in time order, over approved check-in/check-out devices only, recorded in a separate `attendance_punches` table that points to the raw transaction:
  - Exact duplicates of one transaction (same natural key) count once.
  - Consecutive check-ins with no check-out between them form one repetition group: the first is **used**, the rest are **repeat**, with the reason. Consecutive check-outs: the last is used, earlier ones are repeat.
  - A check-out followed by a check-in is a genuine break: both are kept, however close in time.
  - Restaurant punches are never part of attendance grouping.
  - Grouping never crosses more than a configurable gap (default 16 hours) so separate shifts are not merged; it never moves a transaction to another day or shift (shift assignment is spec 503/later).
  - Each cleaned punch keeps: transaction id, included/excluded, repetition group id, reason code, processing run id. Cleanup is deterministic and re-runnable: re-running it for a person and date range produces the same result; results of earlier runs are kept (superseded, not deleted).
- **FR-007 Restaurant usage** (PRD §15): per person per day, one meal count regardless of how many restaurant punches; repeats are noted. Import-row duplicates (same natural key) are distinguished from genuine repeated punches (different minutes). Non-employees are counted under their department label.
- **FR-008 Incremental re-processing**: after a commit, cleanup re-runs only for affected people and dates (the dates in the batch ± 1 day for overnight shifts), and after a device approval or change only for that device's affected punches. A `processing_runs` row records what was run and why.
- **FR-009 Data issues**: a `data_issues` table (reused by later specs) with type, company, batch, subject (person code / device), date range, status (`open` / `resolved` / `dismissed`), resolution note. This spec raises: unknown ID, device pending approval, rows with errors. Device outages are spec 503's (they need expected-attendance context).
- **FR-010 Screens** (Filament admin, HR and platform admin): attendance upload (upload → mapping → coverage confirmation → preview → commit); batches list with original-file download; devices (approve, change role/site with effective date); data issues list; a person's punches for a date range showing raw and cleaned punches side by side with reasons (feeds the 505 profile later). English first, Arabic RTL; codes, times and serials LTR.
- **FR-011 Permissions and isolation**: HR of the company and platform admins only. Every new table carries `company_id` with composite FKs and isolation tests; original files downloadable only by those users.
- **FR-012 Audit**: every commit, device approval/change, issue resolution and processing run writes `audit_logs`; raw transactions, transaction sources and batches are append-only (triggers).
- **FR-013 Scale**: a file of ~5,000 rows previews and commits within a single request today; files up to ~200,000 rows (a month for 1,000+ people) must work: commit and cleanup run as queued jobs with progress, resumable and idempotent (PRD §23).
- **FR-014 Tests (Pest)**: tenant isolation for every table and route; re-upload and overlapping upload create no duplicate transactions or counts; exact duplicates count once; consecutive check-ins 15 minutes apart → one used + one repeat, no review; check-out then check-in kept as two intervals; repeated check-outs → last used; restaurant punches never in attendance and counted once per person per day with repetition noted; pending-device punches unused until approval, then processed; unknown ID → non-employee or data issue by department label; coverage suggested from the file name; cleanup re-run is idempotent; title row skipped; times parsed in Asia/Baghdad; a generated anonymised fixture with the sample's header and row patterns (no real names committed).

## Out of scope

Shift inference, daily sessions, lateness, early departure, short hours, missing punches, absence, device-outage detection (503 and later); leave (504); profile and dashboard (505); overtime; holidays.
