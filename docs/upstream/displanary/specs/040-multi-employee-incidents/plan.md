# Implementation Plan: Multi-Employee Incidents

**Branch**: `040-multi-employee-incidents` | **Spec**: [spec.md](spec.md)

## Existing code (read first)
- Case lifecycle: `app/Services/Cases/CaseOpening.php` (open a draft → checks: duplicates, conflicts, prior cases, responsible-person pattern), `CaseWorkflow.php` (the only writer of status), `CaseClosure.php`, `CaseLinks.php` (manual `related` links, feature 022), `CommitteeSessionService.php` (+ `app/Livewire/Cases/RecordSession.php`), `DefenseLetterFlow.php`, `Deadlines.php`.
- Reports: `app/Services/Reports/ReportService.php`, `app/Livewire/Reports/SubmitReport.php`, `Inbox.php` (conversion), `app/Livewire/Cases/CreateCase.php`.
- Schema: `database/migrations/2026_10_04_201000_create_domain_tables.php` (`cases`, `violation_reports`, `committee_session_attendances` unique per case+member), composite tenant FKs pattern, append-only triggers pattern.
- AI payload builders under `app/Ai/*` (masking, minimal payload).
- UI: `resources/views/livewire/cases/show-case.blade.php`, `cases/board.blade.php`, DESIGN.md.

## Design
- **Schema**: `incidents` (id, company_id, branch_id, created_by_user_id, timestamps, unique(company_id,id)); `cases.incident_id` nullable with composite tenant FK; `violation_report_employees` (company_id, violation_report_id, employee_id, unique pair). Keep `violation_reports.employee_id` for single-employee reports (first named employee mirrored there for back-compat). A DB trigger or model guard refuses changing a non-null `cases.incident_id`.
- **Service** `app/Services/Cases/IncidentService.php` (business logic out of Livewire, CLAUDE.md §19): `createFromReport`, `createForEmployees`, `addEmployee`, `updateSharedFacts`, `members(viewer)`. Each case is still created/opened through `CaseOpening` so every check runs per employee.
- **Session**: `CommitteeSessionService::recordForIncident(incident, attendees, minutes, perCase[outcome, votes], actor)` loops the eligible cases calling the existing per-case logic inside one transaction; returns skipped cases with the reason. Livewire: incident mode of `RecordSession` (or a small `RecordIncidentSession` component) reached from any eligible case page.
- **Facts**: shared fields are stored on each case (as today) and copied by `updateSharedFacts`; refusal for cases with `defense_letter_issued_at`. No new read path for documents.
- **Visibility**: `members(viewer)` filters with `CaseVisibility::for($viewer)`.
- **Privacy test**: build the defense/recommendations payload for one case of an incident and assert other members' names are absent.
- Audit/case events: `incident.created`, `incident.employee_added`, `incident.facts_updated`, `incident.session_recorded` (append-only loggers already exist).

## Tests
Report with 3 employees → 3 cases in one incident; New case with 2 employees; shared-facts edit before/after issuance; add employee; closing one case leaves others; incident session applies to ready cases only with per-case quorum and conflict refusal; tenancy (foreign incident id rejected, composite FK); visibility filtering of the group; privacy of payloads/documents; incident_id immutability; translations, behaviour inventory, browser smoke for the incident panel, Pint, full suite.

## Plan review resolutions

These resolutions override earlier sections where they differ.

### Blockers

- **Opening sequence and duplicate review:** `CaseDrafts::create` creates a draft; `CaseOpening::open` performs the legal opening checks and writes the `open` status through `CaseWorkflow`. The existing New case screen has a separate duplicate review before opening. Create each incident member as a draft through `CaseDrafts`, preserve the duplicate review per employee, and open each chosen draft through `CaseOpening`. Do not equate draft creation with legal opening or bypass the review in bulk actions.
- **Report conversion cardinality:** `violation_reports.case_id` is singular and `ReportService::convert` currently links one case. Preserve it as the first case for compatibility, but all cases created from a multi-employee report must carry `violation_report_id` and share `incident_id`. Reject the existing-case duplicate-link shortcut for a multi-employee report because it cannot represent every named employee. Validate a unique, nonempty employee list in the report's branch and tenant; mirror the first employee in `employee_id`.
- **Issued-fact freeze:** Updating only unissued members after one letter is issued would split supposedly shared facts. Refuse an incident-wide fact edit when **any** member has `defense_letter_issued_at`; use the existing per-case correction path for later changes. Lock the incident and member rows in one transaction. Add a database guard on `cases.incident_id` to prevent any membership update after insertion, including bulk SQL updates; the model guard supplies a readable error. New members are inserted with their incident ID already set.
- **Draft consistency:** Shared fact edits are permitted while every member is still in draft or open and none has a document draft. A document draft may already contain the old facts; use its existing edit/correction path instead of silently changing the source beneath it. Invalidate each member's case-specific description after a shared edit so HR reviews that wording again.
- **Session votes and privacy:** `CommitteeSessionService::recordSession` takes votes inside its attendee list and overwrites per-case attendance rows. Incident session input therefore needs one attendance selection, one chair, one author, one common minutes entry, and a separate vote/outcome/defense-acceptance set for each ready case. Recheck status, mandate, branch, conflicts and quorum per case under locks and make all selected cases atomic. A shared minutes note can mention other employees and would enter a per-case AI payload or Doc A. Require the operator to enter case-safe minutes for each employee (or redact the common note before saving to the case); only case-safe minutes may reach the per-case drafting path. Skip unready cases, but fail the transaction for invalid selected cases rather than silently dropping them.
- **Later sessions:** A member case whose session already reached a majority is complete for incident session selection. A later-ready employee can have a new session without re-recording the completed cases; a case without majority remains eligible for a new vote.
- **Mandate mismatch:** If ready cases have different effective committee mandates or conflict exclusions, their common attendance may fail per-case validation. Keep the existing single-case session route available for an incident member so HR can record legally valid separate sessions rather than weakening either case's mandate or quorum checks.
- **Shared facts may identify another employee:** A shared description, witness list, intake answer, attachment, or responsible-person field can identify another incident member. Copying it to all cases does not make it safe for employee-facing documents or AI payloads. Keep raw shared evidence in internal case context; require explicit case-specific, reviewed wording for legal drafts and do not attach another employee's response or documents. Do not send the incident member list to AI. Test both payloads and issued document content with another member's name in the shared source text.
- **Incident intake minimisation:** Shared report intake answers are internal evidence and are omitted from a member's defense-letter AI payload; HR carries the relevant facts into that member's reviewed description. A responsible-person field naming another incident member is likewise omitted from that payload. Existing single-case payloads are unchanged.
- **Later member privacy:** Refuse adding an employee to an incident when an already-issued member document names that employee. Issued documents cannot be rewritten to make a new grouping private.
- **Closure semantics:** `CaseClosure::closeWithoutPenalty` is not a general draft removal or cancellation path. Add a reasoned, audited HR closure path through `CaseWorkflow` only for statuses where the state machine permits it; do not delete a member, mutate incident membership, or fabricate a recommendation merely to close a draft. If the state machine has no lawful route from a status, leave it open until its existing closure requirements are met.

### Should fix

- **Visibility:** Fetch member rows exclusively with `CaseVisibility::for($viewer)` and scope by tenant and `incident_id`; do not hydrate all members and filter in Blade. Board counts or badges must not reveal invisible member names or counts. HR incident controls must also check `create`/`update` policy, role and branch access on every action.
- **Related links:** Incident siblings are excluded from the manual related-case picker and linking guard. Membership is already their relationship; no duplicate `case_links` row or related-case AI context is created.
- **Schema integrity:** Use new migrations only. Give incidents and report employees `company_id` and composite FKs matching the domain schema; enforce incident/case branch agreement and one employee per incident with service checks and database constraints where practical. Preserve append-only case/audit/AI logs and use the existing loggers for each case mutation.
- **Source of truth:** Copying shared facts into case columns is consistent with current document readers, but later additions must copy the incident's current permitted facts; never take another case's response, status, deadlines, decision, document, or personal fields. One report attachment remains report evidence, subject to per-case document and AI minimisation.
- **Presentation and verification:** Keep the existing single-case controls working. Add en/ar translations and update the UI behaviour inventory for each new binding; use Western digits and the Departures tokens. Test tenant rejection, membership immutability, per-employee clocks, session rollback, and AI/document privacy. Docker gates are delegated to the orchestrator because this checkout has no Docker access.
